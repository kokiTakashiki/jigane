# 方針、実装、セキュリティのレビュー

[README に戻る](../README.md)

jigane は、レビューを方針、実装、セキュリティの三つの群に分け、利用者の Claude Code で解析します。群ごとに、問う観点が決まっています。

## 方針

方針のレビューは、変更や設計が目的に合っているかを確かめます。コードの実装は確かめないため、実際のコードをレビューの対象にせず、判断の地図の図と表だけを読むのが特徴です。コードの実装のレビューは、「[実装](#実装)」のレビューで行います。

PR と範囲のレビューの方針は、図の起動に加えて、設計の原則（P1〜P4）ごとに一本ずつ、最大五本を走らせます。図の起動は M0〜M7 を問い、常に走ります。原則の起動は一本につき一つの P だけを問い、その原則を問える形が図にあるときだけ走ります。形の無い原則は見送りで、失敗ではありません。原則の起動が「図から確かめられない」と捨てた候補は、nit にも実装のレビューへの引き継ぎにもしません。図の起動は claude-sonnet-5-5 で上限 0.36 USD です。原則の起動は claude-haiku-5-5 で 1 本の上限 0.02 USD です。設計書のレビューは一本です。

図の形の方針は、プロンプトの大きさと出力の見込みから見積もった額が 1 本の上限以上の起動を見送ります。式と、見送りが始まる大きさは [cost.md](cost.md) にあります。`jigane estimate` の `input_cost_usd` は、図の形では出力の見込みを含む額です。

原則ごとに問える形は次のとおりです。読み取りが無い言語の図は、形が無いものとして扱います。

| 原則 | 起動が走る形 |
| --- | --- |
| P1 | 値の組の表、または同じ項目を持つ型の表 |
| P2 | 足した公開の口と呼ぶ側の表、または実装が一つの抽象があるクラス図 |
| P3 | 値の組の表、判別の表、クラス図の継承の辺、引数を三つ以上足した関数のどれか |
| P4 | シーケンス図 |

観点は次のとおりです。M3 は設計書のレビューだけで、M5 はレビューボットのコメントがある PR のレビューだけで使います。

| 観点 | 名前 | 問うこと |
| --- | --- | --- |
| M0 | 前提 | なぜこの変更が要るのか。既製の仕組みで補えないか |
| M1 | 宣言と実現 | 宣言した内容を実現できているか |
| M2 | 道筋 | この分け方や依存の向きを続けた先で、目的に近づくか |
| M3 | いまの構造との整合 | 設計書が書いた形が、いまのコードの形と矛盾しないか |
| M4 | 利用者に向けたインターフェース | 公開の契約や保存の形が、後から直しにくい形になっていないか |
| M5 | 指摘への対応 | レビューボットの指摘に応じた変更が妥当か |
| M6 | 技術選定 | 選んだ技術は目的に最適か。自作した仕組みを既製の道具で置き換えられないか |
| M7 | 単純さ | 共変更の表と値の組の表に載った形を、写しを減らし、判別を型に任せて、より単純に表せないか |

## 実装

コードの細部の不具合と品質を問います。実装の群は、レビューの対象の差分やファイルを、大きさが揃うように最大 4 つの組（シャード）に分け、組ごとに同時に起動して読みます。そのうえで、見つけた指摘を検証役が敵対的に確かめます。

観点は三つの系統に分かれます。D は、コードの不具合と品質を問います。P は、設計の原則を、変更した関数やクラスの単位で問います。P1〜P4 は群に属さず、方針と実装の両方の群で問う原則です。T は、テストと検査の規約を問います。具体的には、検査をどこから調達したか、環境への依存をどう断ったか、条件付きの skip が無いか、機械のゲートとレビューの規範をどう分けたかです。D5 もテストを扱いますが、個々のテストが変更を検証しているかというテストの中身を問うので、D に入れています。観点は次のとおりです。

| 観点 | 問うこと |
| --- | --- |
| D1 | 不具合、ロジックの誤り、境界条件、両分岐の考慮漏れ |
| D2 | 空、欠落、不正な形式、重複したデータの扱い、握りつぶされたエラー、途中で失敗したときに残る副作用 |
| D3 | 同じ差分の中で同じ意味を持つ処理どうしの、検証、正規化、エラー処理、優先順位の食い違い |
| D4 | 共通の処理に条件なしで足した変更が、変更していない分岐、モード、種別にまで効いてしまう箇所 |
| D5 | テストの弱さ。変更した分岐や境界を検証していない、意図した挙動が壊れても通るアサーション |
| D6 | 変更後の挙動と食い違うコメント、文書、設定例、変更で参照されなくなったコード |
| D7 | 命名、正規化、スタイル、フォーマットの一貫性 |
| D8 | typo、コメントの言い回し、可読性、重複、簡素化できる箇所 |
| D9 | より良い代替表現、別の書き方、マイクロ最適化 |
| D10 | 欠落を許す真偽値の型（`bool \| None` など）で三つの状態を表している箇所 |
| P1 | 単一の情報源。同じ知識（値の組、型の項目、規則）を一か所だけに置いているか |
| P2 | YAGNI。今の呼ぶ側が使わない公開の関数、引数、列挙の値や、実装が一つしかない抽象を足していないか |
| P3 | KISS。同じことをより単純な形で書けないか |
| P4 | 関心の分離。変更した関数やクラスが、自身の責務とは別の理由で変わる処理を、直接抱え込んでいないか。呼び先の本体を読み、書く先、送る先、変える状態で確かめる。当てはまらない場面：全体をつなぐことが役割の入口（コマンドの入口、組み立ての根）。 |
| T1 | 新設または変更した検査が、既製のリンタ、その設定、自作の順で調達されているか |
| T2 | テストが環境への依存（時刻、乱数、ネットワーク、実行順など）を、無効化、二値化、検出の順で断っているか |
| T3 | 「道具があれば走り、無ければ skip」する条件付きの skip が無いか |
| T4 | 構文と構造で白黒がつく規約だけを機械のゲートに置き、意味の判断が要る規約をレビューの規範として分けているか |

## セキュリティ

セキュリティの弱点を問います。モバイルアプリのコードは OWASP MASVS に、バックエンドのコードは OWASP ASVS に照らし、指摘には根拠にした体系の識別子を添えます。実装の群と同じく、シャードに分けて読み、指摘を敵対的に検証します。MCP は任意で、`--mcps` で選んだときだけ使います。使い分けは「[セキュリティの群の MCP の使い分け](security-mcp.md#セキュリティの群の-mcp-の使い分け)」の節に書いています。
