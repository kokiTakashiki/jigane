# jigane 0.1.9 のお知らせ

0.1.9 の変更を、機能追加、仕様変更、不具合修正に分けて示します。一つずつの変更は、続く「変えたこと」の表にあります。

## 機能追加

`jigane hold` に、保留の理由を残せるようになりました。

jigane の内部を確かめる `jigane debug` を足しました。

リポジトリが定めた開発方針とセキュリティ指針の文書を、レビューに渡せるようになりました。

## 仕様変更

レビュー対象のリポジトリの中身から、jigane が意図しないコマンドの起動やファイルの読み取りを起こされないように、対策を固めました。

データの置き場（環境変数 `JIGANE_HOME` が指すディレクトリ）の権限が広すぎるときは、書き込みを止めるようにしました。

環境変数 `JIGANE_CLAUDE_BINARY` は、絶対パスだけを受けます。

`--max-budget-usd-per-call` は、上限として効かない値を拒みます。

外部の言語プラグインのインターフェースの名前が変わります。プラグインを書いている人は、直す必要があります。

レビューの保存形式のバージョンが上がりました。0.1.8 までのレビューは、作り直しが要ることがあります。

## 不具合修正

Windows で、同じリポジトリのレビューを並行して作ると、レビューの保存先のディレクトリが誤って拒まれることがありました。これを直しました。

## 想定される質問

### 更新の後に、必要な操作はありますか

文法の取得のやり直しは要りません。Claude Code の下限（2.1.308）と文法のバージョンは変えていません。

レビューの保存物の形式が変わりました。保存物には、保存したときの実行環境（文法が引けるか、アダプタが返す文面など）で決まる値が書かれており、環境が変わると、読み直すたびに今の環境と食い違っていました。

0.1.9 は、保存物のフィールドを入力から決まる値に絞り、その形の変更を一度のバージョンの引き上げにまとめました。古いバージョンを読み込みのたびに移す処理は、構造を変えるたびに増えて読み込みの経路を複雑にしていたため、移さずに作り直しにしています。

`runs.json` の JSON の構造のバージョンが 3 から 4 に上がります。`runs.json` は、群を一度でも走らせたレビューにあります。0.1.8 までに群を走らせたレビューは、この jigane では開けません。

`show`、`run`、`usage`、`estimate` などの `runs.json` を読む副コマンドが、「このレビューは古い形式のため、この jigane では開けません」と示して止まります。`jigane new` でレビューを作り直してください。以前の pick、object、hold の記録は引き継がれません。

古いレビューは `jigane delete <レビュー>` で消せます（確認が出ます）。`jigane list` は、これらのレビューをそのまま一覧に出します。

群を走らせていないレビューは、これまでどおり開けます。

`runs.json` には、各回の起動時刻 `started_at` が加わります。

`gates.json` のバージョンも 4 に上がりますが、形は変わらず、古いバージョンは読むときに自動で移ります。

0.1.9 で作ったり更新したりしたレビューを 0.1.8 の jigane で読むと、「runs.json の形の版 4 は、この jigane が読める版 3 より新しいです。」というエラーで止まります。0.1.8 と行き来するときは、jigane を更新してください。

0.1.9 からは、新しいバージョンの jigane が作ったファイルを読むと、jigane は止まって更新を案内します。

0.1.8 までの文は、何が起きたかも何をすればよいかも分からなかったためです。

入れた方法に合わせて、次のコマンドで更新します。

`uv tool install jigane` で入れた場合：

```bash
uv tool upgrade jigane
```

`pipx install jigane` で入れた場合：

```bash
pipx upgrade jigane
```

### --max-budget-usd-per-call に渡せない値はありますか

`nan`、`inf`、`-inf`、0、負の値、数値でない文字列は、受けません。`jigane estimate`、`jigane run`、`jigane debug prompt` が、起動の前に引数の誤りとして止まります。

0.1.8 までは、`nan` と `inf` が上限として効かないまま通っていました。

上限を決めるスクリプトで、これらの値を渡していないか確かめてください。

有限で 0 より大きい値は、これまでどおり受けます。

### ワーキングツリーのファイルの読み取りは、どう変わりましたか

jigane は、レビュー対象のワーキングツリーのファイルを、次の場面で読みます。

- 反証役が示した位置の抜粋
- 値の集合の表のための定義の確認
- 設計書と、設計書に付属する文書（`jigane new design-doc` と `jigane refresh`）
- リポジトリの設定ファイル `.jigane.toml`

0.1.9 から、この読み取りは、シンボリックリンクを辿らず、通常のファイルだけを、大きさの上限（1,000,000 バイト）の内で読みます。レビュー対象のワーキングツリーの中に、外のファイルを指すリンクがあっても、その先は読みません。

リンクを辿ると、レビュー対象のリポジトリの外にあるファイルを読んでしまうためです。

通常のファイルだけで組んだワーキングツリーのレビューは、これまでと変わりません。

読めなかったときの扱いは、場面で分かれます。抜粋と定義の確認では、リンクや上限を超えるファイルを、読めないものとして扱います。

設計書と付属の文書、`.jigane.toml` では、黙って読み飛ばさずに止まります。

`.jigane.toml` を読み飛ばすと、設定した除外や機微の指定が効かないまま進むためです。

止まったときは、原因を示すエラーが出ます。

- 設計書や付属の文書がシンボリックリンクのとき、またはワーキングツリーの外を指すとき：「シンボリックリンクか、木の外を指しています」と示します。通常のファイルに置き換えてください。
- 設計書や付属の文書が 1,000,000 バイトを超えるとき：「大きすぎます（上限 1000000 バイト）」と示します。文書を小さくしてください。
- `.jigane.toml` がシンボリックリンク、ワーキングツリーの外を指す、通常のファイルでない、1,000,000 バイトを超える、のいずれかのとき：その旨を示して止まります。通常のファイルに置き換えるか、小さくしてから、もう一度実行してください。

Windows では、ファイルへのパスの途中にあるディレクトリがシンボリックリンクやジャンクションのときも、同じく拒みます。

### JIGANE_CLAUDE_BINARY に渡せない値はありますか

環境変数 `JIGANE_CLAUDE_BINARY` は、起動する `claude` の実行ファイルを差し替えるためのものです。

0.1.9 から、絶対パスだけを受けます。`./claude` のような相対パスや、`claude` のような名前だけの値は、作業ディレクトリによって別の実体を指しうるため、起動の前に「絶対パスで指定する」というエラーで止まります。

空の値と未設定は、これまでどおり `claude` を使います。

この環境変数を設定しているスクリプトや設定は、絶対パスに直してください。たとえば `/usr/local/bin/claude` のように書きます。

### PATH の探索は、どう変わりましたか

jigane は、`git`、`gh`、`claude` を `PATH` から探します。0.1.9 から、`PATH` のうち絶対パスの項目だけを使います。

空の項目と、相対パスの項目（direnv の `.envrc` が足すものなど）は、作業ディレクトリの中を指して、レビュー対象のリポジトリに置かれた同名の実行ファイルを選んでしまうことがあるため、飛ばします。

`PATH` に絶対パスで `git` などが入っていれば、これまでと変わりません。

相対パスの項目だけが `git` や `claude` の場所だった環境では、「実行ファイルが見つかりません」で止まります。絶対パスの項目を `PATH` に足してください。

### git の起動は、どう変わりましたか

jigane は、レビュー対象のリポジトリで git を呼びます。リポジトリの設定やフックが、jigane の git の呼び出しの中で別のコマンドを起動しないように、0.1.9 から次のとおりにしました。

- すべての git の呼び出しで、`core.fsmonitor` を無効にし、フックを探しても何も見つからない状態にし、ページャを使いません。
- `diff`、`show`、`log` では、外部 diff（`--no-ext-diff`）と `textconv`（`--no-textconv`）を使いません。
- `log` では、署名の確かめ（`log.showSignature`）を無効にします。署名の確かめが、リポジトリの設定の `gpg.program` を起動することを防ぎます。
- `fetch` では、`--upload-pack=git-upload-pack` を明示します。リポジトリの設定の `remote.<名前>.uploadpack` は使われません。

あわせて、PR のベースのツリーの展開で `git archive` をやめました。

`git archive` は、リポジトリの設定の filter（smudge）を起動しうるためです。

0.1.9 は、コミットに入っているファイルのバイト列を、そのまま書き出します。

外を指すシンボリックリンクと絶対パスのリンクを含むツリーを拒む点は、これまでと同じです。拒んだときは、途中まで書いたファイルを残さず、拒んだ理由を示します。

この展開の変更で、`.gitattributes` の効き方が変わります。`git archive` は属性を適用して書き出していましたが、0.1.9 は適用しません。

PR のレビューは、変更前のツリーと変更後のツリーの両方を、この形で展開します。

- `export-ignore` を付けたファイルも展開します。以前は、展開から外れていました。
- `export-subst` を付けたファイルは、`$Format:%h$` のような置換前の文字列のまま展開します。以前は、コミットの情報に置き換わっていました。
- `text` や `eol=crlf` のような改行の指定は適用せず、コミットに入っている改行のままです。以前は、指定に従って変換していました。

リポジトリ自身のフックや、上の項目に当たる設定に頼って git の動きを変えている場合、jigane の中ではそれが効きません。

jigane は、レビュー対象に置かれたものを信用せずに動くためです。

認証の設定（`credential.helper`）と SSH の設定（`core.sshCommand`）は塞いでいないので、これまでどおり効きます。

### JIGANE_HOME の権限とシンボリックリンクの扱いは、どう変わりましたか

jigane のデータの置き場（環境変数 `JIGANE_HOME` が指すディレクトリ）には、差分、PR の本文、Claude の出力が平文で入ります。0.1.9 から、他のユーザーに書かれたり、読まれたりしにくいように、次のとおりにしました。

- ルートが無ければ 0700 で作ります。レビューのディレクトリも 0700、保存物のファイルは 0600 で作ります。既にあるルートの権限は変えません。
- 既にあるルートの所有者が実行ユーザーと違うか、group か other に書き込み権限があるときは、書き込みをする副コマンドが止まります。読み取りの権限だけなら止まりません。`show`、`list`、`usage`、`estimate` などの読み取りの副コマンドは、権限が広くても止まりません。Windows の権限は ACL で決まるため、確かめません。
- 保存先のファイルやロックのファイル、保存物のディレクトリがシンボリックリンクのときは、先を辿らず、書かずに止まります。

止まったときの表示と直し方は、次のとおりです。

- 権限が広いとき：「データの置き場の権限が広すぎます。chmod 700 で狭めてください」と示します。`chmod 700 <JIGANE_HOME のディレクトリ>` を実行してください。
- 所有者が違うとき：「データの置き場の所有者が実行ユーザーと違います。所有者のユーザーで実行するか、置き場を自分の所有に移してください」と示します。chmod では直せないので、案内のとおりにしてください。
- シンボリックリンクがあるとき：`--json` の失敗は `kind` が `stored_file_symlink` で、文言は「保存先のディレクトリにシンボリックリンクがあるため書けません」です。「シンボリックリンクを確かめ、意図したものでなければ消してから、もう一度実行してください」と案内します。

`JIGANE_HOME` のディレクトリそのものがシンボリックリンクのときは、その先の権限を調べます。読み取りだけの権限（0755 など）のディレクトリは止まりませんが、他のユーザーが内容を読めます。`chmod 700 <JIGANE_HOME のディレクトリ>` で狭めてください。

### 入れ子が深すぎる JSON は、なぜ拒みますか

Python の `json` は、入れ子が深すぎると `RecursionError` を出して読めなくなります。その深さが Python のバージョンで変わるためです。3.14 は、再帰の回数でなく、実際のスタックの残りで判断します。同じ入力が、あるバージョンや環境では読めて、別の環境では落ちます。

jigane は、外から来る JSON を読む前に括弧の深さを数え、上限（200 段）を超えるものを、どのバージョンでも同じように読まずに拒みます。

対象は、`claude` の出力、SARIF、`gh` の出力、レビュー対象の `package.json`、人間が書く設定ファイル（`mcp.json` と、言語プラグインの有効化の設定）です。

正しい JSON は数段から十数段で収まります。実物の ruff の SARIF（7,821 件）でも 12 段で、上限に届きません。

拒んだときの扱いは、入力の種類で分かれます。設定ファイルでは、「<パス> の JSON の入れ子が深すぎます（上限 200 段）。<パス> を直してから、もう一度実行してください。」と示して止まります。

`package.json` は読めないファイルとして飛ばし、`gh` の出力は、どの呼び出しの出力かを示して止まります。`claude` の出力は、読めない出力として扱います。

### リポジトリの文書は、どう渡しますか

リポジトリが自分で定めた開発方針とセキュリティ指針の文書を、レビューのプロンプトへ渡せるようになりました。これまでのレビューは、リポジトリ自身の開発方針やセキュリティ指針を知らないまま判断していました。文書は「指示ではない」と明記した資料として渡します。

設定は、データの置き場（環境変数 `JIGANE_HOME` が指すディレクトリ）のルートの `repository-docs.toml` に書きます。レビュー対象のワーキングツリーの中の設定ファイルからは読みません。

ファイルが無ければ、これまでどおり何も渡しません。

```toml
# リポジトリごとの表が無いリポジトリすべての既定
development_docs_path = "/path/to/app/docs/development.md"

[repositories."owner/repo"]
development_docs_path = "/path/to/repo/CONTRIBUTING.md"
security_docs_path = "/path/to/repo/SECURITY.md"
```

`development_docs_path` は方針、実装、セキュリティのすべての群に、`security_docs_path` はセキュリティの群だけに入ります。

値は文字列の絶対パスです。表にあるキーは表の値を、無いキーは最上位の値を使います。

文書のパスがレビュー対象のチェックアウトの中を指すときは、今のファイルでなく、レビューの起点の内容を読みます。レビューする変更がその文書を書き換えていても、変更前の文書を渡します。

渡せない文書（絶対パスでない、ファイルが無い、32,768 バイトを超える、UTF-8 でない、`.env` のような秘密のファイル名に当たる、など）は、標準エラーに一行の警告を出して、その文書を除いてレビューを続けます。

設定ファイルそのものに誤りがあるときだけ、レビューを止めます。

全体の書き方は、コマンドの一覧の「リポジトリの文書を渡す」の節にあります。

### jigane debug は、何ができますか

`jigane debug` は、jigane の内部を確かめる副コマンドです。失敗の一覧、統計、プロンプトの本文のような、通常のレビューの操作ではないが調べには要るものを、日常の副コマンドと分けてここに置きました。

出力は暫定で、jigane のバージョンで変わることがあります。

- `jigane debug errors`：jigane が失敗で返す `kind` の一覧を出します。
- `jigane debug prompt <レビュー> <群>`：LLM を起動せずに、その群で起動するときのプロンプトを出します。費用はかかりません。
- `jigane debug run <レビュー> <群> --yes --max-usd <額>`：端末での同意を飛ばして走らせます。AI ツールが非対話で使うための実験的な副コマンドです。`--yes` と、有限で 0 より大きい `--max-usd` の両方が要ります。どちらかが無いときは、引数の誤りとして終了コード 64 で止まります。見込みが `--max-usd` を超えるときは、起動せずに終了コード 2 で止まります。
- `jigane debug stats`：データの置き場（環境変数 `JIGANE_HOME` が指すディレクトリ）にあるレビュー全体の、指摘の数と札をまとめます。
- `jigane debug review-id`：レビューの識別子の文法を示します。

各副コマンドの引数と `--json` の形は、[コマンドの一覧](../commands.md#jigane-debug)にあります。

### hold の理由は、どう残しますか

保留にした理由（どの枝で直すか、人間の承認待ちか、など）は、これまで記録に残らず、後から読み返す人が辿れませんでした。

`jigane hold <レビュー> <指摘>... --reason <理由>` で、保留の理由を残せます。並べたすべての指摘に、同じ理由を記録します。

`--reason` は任意です。付けない `hold` は、これまでどおり成功します。保留にした指摘へ理由なしで打ち直したときは、何も変えず、前の理由を残します。

理由は空白だけにできません。空白だけの理由は「保留の理由が空です。理由を書くか、--reason を付けずに実行してください。」と表示して失敗し、何も記録しません。

理由は `object` の `--reason` と同じく、`show` の表示には出ません。

`--json` の出力と `show --json` の選択のフィールドでは、保留の番号の配列 `held` はそのままで、理由を持つ保留だけを、番号から理由への対応 `hold_reasons` で出します。理由を付けていない保留は、`hold_reasons` に現れません。

`--json` を機械で読むスクリプトは、項目が増えても読めるようにしてください。

`unhold` は保留を外すので、理由も消えます。

理由を持つ保留を、別の扱い（`pick` や `object`）で置き換えたとき、または別の理由を付けた `hold --reason` で書き換えたときは、消える理由を標準エラーに `注: F1 の保留を置き換えました。消えた理由: ...` の一行で示します。

### 文法の取得は、どう変わりましたか

`jigane languages fetch` は、取得の前に、保存先のディレクトリにある文法の共有ライブラリを、記録されたハッシュ（SHA-256）と照合します。

照合は、保存先の共有ライブラリが差し替えられていても、そのコードが jigane の照合より先に読み込まれないようにするためです。

合わないものは、標準エラーに「文法 X のファイルが記録と合わないため、消して取り直します。」と示して消し、取り直します。保存先のディレクトリの外を指すファイルや、読めないファイルは、消さずに止まります。

組み込みの言語の文法の取得に失敗したときは、「組み込みの文法の取得に失敗しました」と示し、追加の言語を取得せずに止まります。

処理の失敗の終了コードで終わります。

取得の失敗を、捕捉されない例外で落とさずに、分かる文で止めるためです。

打ち直すと、最初から取り直します。

### 外部の言語プラグインは、何を直しますか

この質問は、外部の言語プラグインを書いている人だけに関わります。プラグインを使うだけの人は、直すものがありません。

0.1.8 まで、jigane は外部プラグインのアダプタを包んでから使っていたため、プラグインが実装した能力のインターフェース（`DiscriminatorBranchExtractor` や `ImportedModuleExtractor` など）が効いていませんでした。

0.1.9 は包まずに使います。能力のインターフェースを実装していれば、その能力を持つ言語として扱われます。

あわせて、インターフェースの名前を、取り出すものが分かる名前に変えました。`Reader` や `Adapter` のままでは、何をどこから取り出すかが名前から分からなかったためです。旧名の別名は残していません。

プラグイン API のバージョンを 2.0 に上げたため、バージョン 1 を宣言するプラグインは読み込めません。`languages` 以外の副コマンドがエラーで止まります。エラーの文が直し方を案内します。止まったときは `jigane languages disable <名前>` で外せます。

次の表に従って、インターフェース名、メソッド名、値の型、フィールド名を直し、`api_version` に `ApiVersion(2, 0)` を書いてください。

`PLUGIN_API_VERSION` は `jigane.languages.api` から無くなったので、`ApiVersion(2, 0)` を直接書いて宣言します。インターフェースと値の型は、`jigane.languages.api.capabilities` から公開しています。

`ValueSetReader` が二つに分かれたため、値の組と比較の両方を実装した言語だけが、値の組の表の対象になります。

この API は試験的で、バージョンごとに形が変わりえます。

### jigane languages list の出力は、どう変わりましたか

一覧に、`StringLiteralSetExtractor`、`StringLiteralComparisonExtractor`、`TopLevelStringConstantExtractor` の三つのインターフェースが加わります。

`--json` の `interfaces` のキーは、インターフェースの名前を改めても変わらないように、インターフェースの役割を表す固定の識別子（`added_public_names`、`discriminator_flow_steps`、`unsupported_syntax` など）になります。0.1.8 まではクラス名がキーでした。

クラス名のキーを読むスクリプトは、識別子に直してください。項目が増えても読めるようにもしてください。

識別子の一覧は [言語を追加する](../adding-languages.md#インターフェースの識別子) にあります。

プラグイン API のバージョンが古いプラグインの理由の種類は `api_version_old` です。

### show --json の in_reply と selection_note を読むスクリプトは、どう直しますか

`jigane show --json` の指摘ごとのフィールドから、`in_reply` と `selection_note` を消しました。`in_reply` はいつも真、`selection_note` はいつも null で、情報を持たないフィールドでした。

この二つのフィールドを読むスクリプトは、フィールドが無い前提に直してください。たとえば、`in_reply` を条件にした分岐は、その条件を外します。`selection_note` を表示や集計に使っていたなら、その処理を消します。

ほかのフィールドは変わりません。

### 読めないレビューの警告は、どう変わりましたか

`jigane list` は、読めないレビューを一覧から除くときの警告を、他の警告と同じ「警告: 一覧から除きました: …」の一行で出します。

これまでは、この警告だけが書式が違い、jigane の内部のファイル名や `UserWarning` が端末に出ていました。

`jigane estimate` のようにデータの置き場（環境変数 `JIGANE_HOME` が指すディレクトリ）の全件を引く副コマンドでは、除いたレビューごとの警告を出さず、除いた件数と例を一行にまとめ、作り直しの案内を添えます。
