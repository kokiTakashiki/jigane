# jigane 0.1.11 のお知らせ

0.1.11 では、変更を「機能追加」「仕様変更」「不具合修正」の三つに分けて示します。一つずつの変更は、「変えたこと」の表にまとめています。

## 機能追加

リポジトリが `.gitattributes` で `linguist-generated` の印を付けたファイルを、方針のレビューの資料で「生成物」と示すようにしました。対象は、レビュー対象のコミット（head）を持つレビューです。

資料には、head の `.gitattributes` にある印の行の表も載せます。

この印を使うときは、リポジトリの `.gitattributes` に印の行を書きます。

`jigane debug paths` を足しました。jigane が読み書きするデータの置き場（環境変数 JIGANE_HOME で場所を変えられるディレクトリ）のルートと `repository-docs.toml` のパス、およびルートの検査の結果を、何も書かずに確かめられます。

## 仕様変更

`jigane list` 以外の副コマンドが出す、読めない古い記録の警告を、出力の末尾の 1 行にまとめました。

データの置き場のルートまでの途中のディレクトリが無いとき、jigane が新しく作るものを 0700 で作るようにしました。既にあるディレクトリの権限は変えません。

Python の呼ぶ側の表で、関数を値として渡す参照（`key=fn`）と、メソッドの属性の読み出し（`x.prop`）も数えるようにしました。

保存したレビューのファイルを読むとき、シンボリックリンク（Windows ではリパースポイント）なら、辿らずに止めるようにしました。一覧（`jigane list`）では、そのレビューを除きます。

保存したレビューのファイルを読むとき、通常のファイルでないもの（FIFO、デバイス、ディレクトリ）なら、読まずに止めるようにしました。一覧（`jigane list`）では、そのレビューを除きます。

以前は、データの置き場に書き手のいない FIFO があると、ファイルを開く処理や読む処理が戻らなくなっていました。

## 不具合修正

一回の実行の中で同じ読めない古い記録を何度も数えていたため、件数が実際より多く出ることがありました。同じ記録を一度だけ数えるように直しました。

レビューの識別子（`owner/repo#1` など）の末尾に改行が一つ付いていても、拒まずに受け付け、改行を落として扱っていました。識別子の全体が形に合うときだけ受け付け、末尾の改行は拒むように直しました。

## 想定される質問

### 生成物の印は、資料にどう載りますか

方針のレビュー（macro）には、ファイルの本文を渡しません。渡すのは宣言、背景、図と表、前の回の指摘です。

ファイルの冒頭の注意書きは、資料に届きません。そのため、`entrypoints.toml` から `make generate` で作った Makefile と justfile を、同じ手順を三か所に書き写した重複として指摘することがありました。

0.1.11 は、リポジトリの持ち主が `.gitattributes` に書いた `linguist-generated` の印を、資料で伝えます。jigane が印を推測することはありません。

印は、`git check-attr --source` に head のコミットを渡して読みます。ワーキングツリーの内容は読みません。

印を打ち消した行（`-linguist-generated`）と、値を代入した行（`linguist-generated=false` など）は、印として扱いません。

印のあるファイルには、ツリー図のラベルに「生成物」を足します。資料には、次の凡例を足します。

```text
「生成物」は、宣言から機械で生成したファイルで、手で書き写した重複ではない。直すなら生成元を直す。
```

印の行は、「生成物の印」の節に表（ファイル、パターン、印）で載せます。

表は 30 行までで、超えた分は件数だけを書きます。パターンは 160 文字で切ります。大きすぎる `.gitattributes`（1 MB を超えるもの）は表に載せず、その旨を一行書きます。

印は、`.gitattributes` を書く人が決めます。誤った印は、重複の指摘を見送らせるおそれがあります。表を載せるのは、印の付け方そのものを、レビューする側が見られるようにするためです。

`.jigane.toml` の `exclude` に合うファイルには、ラベルを付けません。`exclude` は `*.lock` のように、生成物とは限らないファイルも外すためです。

`exclude` に合うファイルの差分が各群から外れる挙動は、変えていません。印だけを持つファイルの差分は、micro と security の群にも、これまでどおり渡ります。

印を読めないときは、ラベルを付けず、資料に次の一行を書きます。

```text
生成物の印を読めなかった。札が無いことは生成物でないことを意味しない。
```

印を読めないのは、git が失敗したとき、出力をパースできないとき、記録した head が SHA の形でないときです。

head のコミットが存在しないときも、読めなかったと扱います。git 2.54.0 の `git check-attr` は、`--source` のコミットが無くても、空のツリーとして終了コード 0 で終わります。そのままでは「印が無い」と取り違えるため、jigane は先に `git cat-file -e` でコミットの有無を確かめます。

検査するパスが 2000 件を超えるときは、先頭の 2000 件だけ検査します。超えた分は、検査していない旨と件数を資料に書きます。

印を付けるには、`.gitattributes` に `/Makefile linguist-generated` のように書きます。

### jigane debug paths は、何を示しますか

`jigane debug paths` は、jigane が読み書きするパスと、データの置き場のルートの検査の結果を示します。ルートを作らず、何も書きません。

`--json` の出力は、`data_home`、`data_home_check`、`repository_docs_settings` の三つのフィールドを持ちます。`--json` が無いときは、三つを一行ずつ出します。`data_home_check` は `exists`、`stops`、`kind` を持ちます。

読む側は、`kind` の値が増えても誤らないよう、止まるかどうかを `stops` で判定してください。

`kind` の値と意味は、`docs/commands.md` の `jigane debug paths` の表のとおりです。

`debug` の副コマンドの出力は暫定で、jigane のバージョンで変わることがあります。

### 読めない古い記録の警告は、なぜ変わりましたか

古いバージョンの jigane が書いたなどの理由で読めない記録は、`jigane list` が 1 件ずつ理由つきで警告します。これは変えていません。

`list` 以外の副コマンドは、データの置き場の全件を内部で読む間に、同じ警告を出します。0.1.11 は、この警告を次の 1 行にまとめました。

```text
読めない古い記録が N 件あります。理由は `jigane list` で 1 件ずつ見られます。
```

N は件数です。

警告は、出力の末尾に出します。標準出力が端末でないと、出力は終了時にまとめて書かれ、警告が出力より前に見えてしまいます。そのため、警告の前に標準出力を書き出します。

まとめる理由は、`jigane estimate` のようにデータの置き場の全件を読む副コマンドで、古いバージョンの記録 1 件ごとに同じ警告が並ぶのを避けるためです。

### データの置き場までの途中のディレクトリは、どう作られますか

ルートまでの途中のディレクトリが無いとき、jigane が新しく作るものだけを 0700 で作ります。既にあるディレクトリの権限は変えません。

以前は、途中のディレクトリを通常の権限で作っていました。

データの置き場には、差分、PR の本文、Claude の出力が平文で入ります。ルートを他のユーザーに読ませない権限（0700）で作るのは、このためです。

既にあるディレクトリの権限を変えないのは、ホームディレクトリのように、jigane が作っていないものを書き換えないためです。

### Python の呼ぶ側の表は、どう変わりましたか

呼ぶ側の表は、変更した公開の名前を使っている箇所を、資料に示します。

Python の関数は、呼び出しに加えて、値として渡す参照（`key=fn`）も数えます。メソッドは、呼び出しに加えて、属性の読み出し（`@property` の `x.prop` や、呼ばずに渡す `x.m`）も数えます。代入先と `del` の対象は数えません。同じ呼び出しは、一つの箇所として数えます。

以前の呼ぶ側の表は、呼び出しだけを数えていました。

### 保存したレビューのファイルがシンボリックリンクのとき、なぜ止まりますか

jigane は、保存したレビューのファイル（データの置き場の中のファイル）を読むとき、シンボリックリンクを辿らずに止めます。止まるときは、次の文を出します。

```text
<パス> は symlink（Windows ではリパースポイント）です。辿らずに止めます。
```

0.1.11 より前は、保存したレビューのファイルを読む経路のいくつかで、シンボリックリンクを検査していませんでした。0.1.11 は、検査の抜けが見つかった経路で、シンボリックリンクを辿らないようにしました。

`jigane list` は、そのレビューを一覧から除き、読めない記録として数えます。

`jigane delete` は、シンボリックリンクの `review.json` を持つレビューも消せます。

### 保存したレビューのファイルが通常のファイルでないとき、なぜ止まりますか

jigane は、保存したレビューのファイル（データの置き場の中のファイル）を読むとき、開いたファイルが通常のファイルでなければ、読まずに止めます。通常でないファイルは、FIFO、デバイス、ディレクトリです。止まるときは、次の文を出します。

```text
<パス> は通常のファイルではありません。読まずに止めます。
```

以前は、書き手のいない FIFO があると、ファイルを開く処理や読む処理が戻らなくなっていました。

通常のファイルかどうかは、ファイルを開いた後に、開いたファイルそのものを調べて判定します。開く前に調べると、調べてから開くまでの間にファイルを差し替えられるためです。

`jigane list` は、そのレビューを一覧から除き、読めない記録として数えます。

### レビューの識別子の末尾に改行が付いているとき、なぜ拒むようになりましたか

レビューの識別子（`owner/repo#1` など）を受け取る副コマンドは、末尾に改行が一つ付いた識別子を拒まずに受け付け、改行を落として扱っていました。0.1.11 は、識別子の全体が形に合うときだけ受け付けます。末尾の改行は拒みます。

同じ形で入力を検査していた、ほかの箇所も直しました。利用者が渡す入力のうち、`jigane pick`、`jigane object`、`jigane hold` などに渡す指摘とテーマの名前（`F1`、`B1` など）、および `jigane export-reply` と `jigane export-report` の `--template` に渡すテンプレートの名前が、これに当たります。

利用者が渡さない箇所（`jigane flaky` の検査項目の定義、jigane の開発用のスクリプト）も、同じ形に直しました。
