# jigane 0.1.14 のお知らせ

0.1.14 の変更を機能追加、仕様変更、不具合修正に分け、個々の内容を「変えたこと」の表にまとめました。

## 機能追加

MCP を使う Codex のセキュリティレビューでも、群全体の費用の見込みを確認できるようにしました。

## 仕様変更

Codex の方針レビューでは、設計書の起動と、PR やコミット範囲を対象とする最初の図の起動に `gpt-6.2-sol` の `high` を使います。

Codex の実装レビューとセキュリティレビューでは、指摘を探す発見役に `gpt-6-luna` の `high` を使います。

設計書の方針レビューの起動前に使う基準上限を、Claude Code と Codex の両方で 0.55 USD に上げました。

Codex のレビューで、1 回の起動の時間上限を 120 秒から 900 秒に延ばしました。

PR やコミット範囲の方針レビューでは、原則ごとに jigane が組み立てるプロンプトの本文を、Claude Code と Codex で揃えました。

Codex の実装レビューとセキュリティレビューでは、発見役に渡す差分をファイル単位で分けるようにしました。

起動前の費用の検査を Codex にも適用します。資料が上限に達する見込みで止まったら、案内に従って資料を短くするか、レビュー範囲を絞ってください。

Codex の `jigane estimate --json` の `prompt_bytes` は、各プロンプトの本文のバイト数を示します。このフィールドを使うスクリプトは、集計の前提を確認してください。

Codex の差分レビューでは、発見役の指摘を確かめるときにも、レビュー範囲の変更資料を使います。

Windows 上で直接実行する jigane は、レビューの作業場所が UNC パスの場合、モデルの起動前にエラーで止まります。Windows のローカルドライブにリポジトリを置くか、WSL のリポジトリなら WSL の端末内で jigane を実行してください。

## 不具合修正

設計書で名前を挙げた関数を、実際の定義に照合できないことがある不具合を直しました。

方針レビューや発見役の起動がごく短い出力で指摘を返さなかった場合は、レビューに欠けがあることを警告します。

実装とセキュリティの差分レビューでは、`.env` や `*.pem` などの既定の除外名に当たるファイルの変更を誤ってレビューの範囲に含めてしまっても保護が及ぶよう、除外の適用範囲を広げました。内容を変えたファイルも、Git が改名と判定したファイルも、前後どちらかの名前が除外名に当たれば、その差分を反証役と判定役に渡す変更資料から外します。判定役への抜粋には、除外した改名の前後どちらのパスも使いません。Claude Code の起動時には、改名後のパスも読み取り拒否の設定に加えます。

## 想定される質問

### 秘密のファイルはどう保護されますか

0.1.14 の実装レビュー（`micro`）とセキュリティレビュー（`security`）では、PR やコミット範囲の差分を対象に、既定の除外名（`.env` や `*.pem` など）に当たるファイルの保護を広げました。誤ってレビューの範囲に含めてしまっても、発見役の資料に加え、反証役と判定役に渡す変更資料からも対象ファイルの差分を外します。内容を変えたファイルも、Git が改名と判定したファイルも、変更前後どちらかの名前が除外名に当たれば対象です。

判定役に渡す抜粋にも、除外したファイルの改名前後のパスを使いません。内容を変えずに改名した場合も同じです。

Claude Code の起動時には、新しい名前が既定の除外名に当たらなくても、除外したファイルの改名後のパスを読み取り拒否の設定に加えます。

0.1.0〜0.1.13 で Claude Code を使って PR やコミット範囲の差分を `micro` または `security` でレビューしたときは、既定の除外名に当たるファイルを誤ってレビューの範囲に含めてしまうと、次のように保護が及ばないことがありました。

- 指摘を確かめる反証役と判定役の変更資料に、そのファイルの差分が入る可能性がありました。既定の除外名に当たるファイルに変更があり、指摘の検証に進んだ場合です。
- 改名したファイルの内容が、判定役に渡す抜粋に入る可能性がありました。改名前の名前だけが既定の除外名に当たり、反証役がそのファイル内の位置を示した場合です。
- 改名したファイルを、Claude Code のファイル読み取りを使う役が開ける可能性がありました。改名前の名前だけが既定の除外名に当たり、ファイルが変更後のワーキングツリーにあり、その役が起動した場合です。

Codex を使ったレビューは、旧バージョンのこれら三つの不具合の対象外です。

### Windows の共有フォルダーや WSL のリポジトリはどうレビューしますか

Windows 上で直接 `jigane run` や `jigane debug run` を実行したとき、レビューの作業場所が UNC パスなら、モデルを起動せずに終了コード `2` で止まります。通常のネットワーク共有と、Windows から開く `\\wsl$` や `\\wsl.localhost` が対象です。

UNC の作業場所では Claude Code のファイル読み取り制限が適用されることを確認できなかったため、起動前に止めます。

Windows でレビューする場合は、リポジトリを `C:` などのローカルドライブに置き、そのリポジトリでレビューを作成して実行してください。WSL 内のリポジトリは、WSL に jigane をインストールし、WSL の端末でリポジトリを開いてレビューを作成し、実行してください。

### 指摘が 0 件でも終了コード 3 になるのはいつですか

Claude Code と Codex のどちらでも、方針レビューの各起動と、実装レビューまたはセキュリティレビューの発見役の各起動が対象です。いずれかの起動で、有効な応答の指摘が選別や検証の前に 0 件であり、出力が 100 トークン未満と報告された場合は、jigane は警告を出して、レビューの一部が欠けたときの終了コード `3` を返します。

判定は起動ごとに行います。出力トークン数が分かる起動に限り、Codex では推論を含む値を使います。

極端に短い応答で指摘が 0 件の場合は、レビューが済んだと判断できないためです。警告が出たら、もう一度実行するか、別のエージェントで確かめてください。

Codex のレビューがごく短い出力で指摘 0 件のまま終わることがあるため、0.1.14 の公開後に PyPI で 0.1.12 と 0.1.13 を取り下げる（yank する）予定です。バージョンを固定してインストールするとき、pip が取り下げられたバージョンを選ぶと警告が出ます。

### Codex の方針レビューで最初にどのモデルを使いますか

設計書の方針レビューは 1 回の起動で、`gpt-6.2-sol` の `high` を使います。PR やコミット範囲の方針レビューでは、最初の図の起動が対象です。見積もりと実行前の確認には、担当モデルとその単価を反映します。

以前の設定では、設計書のレビューが短い出力で、指摘を返さず終わる例がありました。同じ設計書で指摘を得られた設定を、最初の起動に採用しました。

### Codex で指摘を探すときの設定はどう変わりますか

実装レビューとセキュリティレビューの発見役では、`gpt-6-luna` の `effort` を `low` から `high` に変更しました。費用の見積もりでは、発見役の 1 回の起動につき、出力と推論を合わせて 16,384 トークンと見込みます。

従来の `low` では推論をほとんど行わない試行がありました。`high` で推論と根拠のある指摘を確認できたため、発見役に採用しました。

### 起動前の費用の上限はどう変わりますか

設計書の方針レビューでは、1 回の起動を見送るか判断する既定の基準上限を、両エージェントで 0.55 USD にしました。以前の 0.5 USD では、設計書の資料の費用の見込みが上限に達し、起動前に止まる例がありました。

Codex でも、jigane が起動前に費用を見積もり、上限に達する起動を見送ります。実際の請求額は OpenAI 側で確認してください。

資料が大きすぎるという案内が出たら、理由に挙がった節を短くするか、レビューの範囲を絞ってから、もう一度実行してください。

### レビューの時間上限はどう変わりますか

以前の Codex の時間上限は 1 回の起動につき 120 秒でした。120 秒を超えて完了するレビューがあるため、Claude Code と同じ 900 秒に揃えました。

### 方針レビューの原則に渡す資料はどう変わりますか

PR やコミット範囲の方針レビューでは、原則ごとに jigane が組み立てるプロンプトの本文を揃えました。エージェントを切り替えても同じ根拠を基に原則を確認できるようにするためです。

### Codex の発見役に差分をどう分けて渡しますか

実装とセキュリティの差分レビューでは、変更をファイル単位でまとめ、発見役に渡します。Codex も Claude Code と同じ分け方を使い、起動回数の見積もりもその計画に基づきます。

### 見積もりのバイト数を使うスクリプトはどう見直しますか

Codex の `jigane estimate --json` の `prompt_bytes` は、プロンプト本文の UTF-8 のバイト数です。モデルの動作を制限するために jigane が付ける追加の指示は、本文のバイト数の集計から外しました。起動ごとの本文の入力概算もこのバイト数を使います。

群全体の費用の見込みを読む場合は `expected.total_usd` を使ってください。このフィールドの計算には追加の指示の入力分と、出力および推論の見込みが入ります。

### MCP を使う場合の見積もりはどう変わりますか

セキュリティレビューに MCP サーバを選ぶと、Claude Code と Codex の両方で、群全体の費用に初期起動ごとの資料取得を見込みます。それぞれのサーバに 1 回問い合わせ、応答を受け取る分です。

資料を取得するのは、指摘を探す発見役です。見積もりに取得分を加えると、MCP を使う場合の費用も実行前に比較できます。Codex では、費用を見積もれた場合は実行前の確認にも群の見込みが出ます。

### Codex は差分レビューの指摘を何で確かめますか

実装の差分レビューとセキュリティの差分レビューでは、Claude Code と同じレビュー範囲の変更資料を使って指摘を確かめます。Codex は、この資料に含まれる根拠だけで判定します。根拠を資料の中で確認できない候補は「未検証」として残します。

### 設計書で挙げた関数の名前はどう照合しますか

同じ節で型と関数の名前を挙げ、その型に該当するメンバーがなければ、ファイルの最上位にある関数の定義も探します。以前の照合では、この条件で実在する関数を見落とすことがありました。

例えば Python のモジュール直下の関数や Swift のトップレベル関数が対象です。同名の関数が複数のファイルにあり、一つに絞れない場合は、照合結果に「曖昧」と表示します。
