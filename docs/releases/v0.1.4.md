## 想定される質問

### なぜ観点を識別子で保存するようにしたのですか

0.1.4 では、指摘の観点（D1、M2 など）の持ち方を改めました。これまでは表示の番号をそのまま保存していたため、番号を振り直すと、過去の指摘の観点の意味が変わってしまうおそれがありました。0.1.4 からは、観点ごとに変わらない識別子（UUID）を振り、置き場にはその識別子を保存します。表示には、これまでどおり番号を使います。

### 0.1.3 で作ったレビューは、0.1.4 でも読めますか

読めます。0.1.3 以前の形式の記録は、0.1.4 がそのまま読み替えるので、更新の前に手を加える必要はありません。

0.1.4 がレビューの指摘の記録（`findings.json` と `findings_history.json`）を書くとき、記録は新しい形式（版 4）になります。群を実行したときや、レビューを新しい先端へ更新したときなどです。読むだけのとき（`jigane show` など）は書き直しません。

### 0.1.4 に上げた後で、0.1.3 に戻せますか

版 4 で書き直した記録は、0.1.3 以前の jigane では読めません。更新した後に古い版へ戻す予定があるときは、更新の前に置き場を写しておいてください。

### なぜ実装の観点の番号を振り直したのですか

実装の群の観点は、これまで D5 が欠けた並びでした。0.1.4 ではこの欠番を詰め、D6 以降の番号を一つずつ繰り上げます。観点の中身は変わりません。過去のレビューも、表示するときは新しい番号で出ます。

| 0.1.3 までの番号 | 0.1.4 からの番号 | 問うこと |
| --- | --- | --- |
| D6 | D5 | テストの弱さ |
| D7 | D6 | 変更後の挙動と食い違うコメント、文書、設定例、参照されなくなったコード |
| D8 | D7 | 命名、正規化、スタイル、フォーマットの一貫性 |
| D9 | D8 | typo、コメントの言い回し、可読性、重複、簡素化できる箇所 |
| D10 | D9 | より良い代替表現、別の書き方、マイクロ最適化 |
| D11 | D10 | 欠落を許す真偽値の型で三つの状態を表している箇所 |

D1 から D4、T1 から T4、方針の M0 から M6、セキュリティの観点の番号は変わりません。

jigane run の案内に出す観点の範囲も、観点の表から引くようにしました。`jigane run` の案内に出す範囲は、方針の群が M0〜M7 と P1〜P4、実装の群が D1〜D10、P1〜P4、T1〜T4 です。

### 保存した指摘の D5 は、どの観点を指しますか

**0.1.3 の D5 と 0.1.4 の D5 は別のものを指します。** 0.1.3 では D5 は欠番で、セキュリティの群が扱うものとされていました。0.1.4 の D5 は、テストの弱さです。

### 番号で観点を絞り込むスクリプトは、どう直せばよいですか

番号で観点を絞り込むスクリプトや、番号を書いたメモを使っているときは、上の表に合わせて読み替えてください。

番号は今回のように振り直すことがありますが、`viewpoint_id` は変わりません。JSON の出力を読み込んで集計や絞り込みをするときは、`viewpoint_id` で観点を引いてください。

### JSON の出力に増えた項目には、何が入りますか

`--json` の出力で観点を出すところに、新しい項目を三つ足しました。これまでの `viewpoint`（表示の番号）も残しています。

- `viewpoint_id`: 観点の変わらない識別子（UUID）です。
- `viewpoint_name`: 観点の名前です。方針の観点の「道筋」などが入ります。名前の無い観点では `null` です。
- `viewpoint_kind`: 観点の種別です。`defect`、`test_convention`、`policy`、`security`、`design_principle` のいずれかです。`design_principle` は、設計の基礎の原則（単一の情報源など）の観点です。

観点ではない項目（捨てた候補から写した nit など）では、三つとも `null` です。

### jigane usage の表で、同じ役の行が二つに分かれたのはなぜですか

プロンプトの型のバージョンが変わったためです。jigane が LLM に渡すプロンプトは、jigane の側で決まっている文面（雛形と観点の一覧）に、レビューのたびに差し込む中身（PR の差分や方針の資料など）を入れて作ります。プロンプトの型のバージョンは、差し込む前の文面から求めた 12 文字の値です。文面が同じなら同じ値になり、どこか一か所でも変われば別の値になります。差し込む中身は値に入らないので、別の PR をレビューしても値は変わりません。

`jigane usage` の表では「プロンプトの型の版」の列に出ます。0.1.3 までの見出しは「プロンプト版」でした。CSV と JSON の項目名 `prompt_version` は変わりません。表はこの値ごとに行を分け、プロンプトの型を変える前と後の使用量を混ぜずに示します。0.1.4 では観点の表とプロンプトの雛形を改めたため、値が変わりました。0.1.3 で始めたレビューを 0.1.4 で続けて実行すると、同じ役の行が、0.1.3 の値の行と 0.1.4 の値の行に分かれます。

### 方針のレビューの結果に、新しい観点の指摘は出ますか

方針の群に、観点 M7「単純さ」を足しました。共変更の表と値の組の表に載った形を、写しを減らし、判別を型に任せて、より単純に表せないかを問います。方針のレビューの結果に M7 の指摘が出ることがあります。

観点 M0「前提」の問いを、「既存の仕組みで補えないか」から「既製の仕組みで補えないか」に改めました。PR のレビューと設計書のレビューの両方で変わります。方針の群が照らす基準の表には、識別子に表示の値を使う形を足しました。その値が保存物に入るか、境を越えて比べられるときに、変わらない識別子と表示の値を分けられないかを問います。

設計の基礎の原則 P1 から P4 を、観点の表に足しました。種別は `design_principle` です。P1 は単一の情報源、P2 は YAGNI、P3 は KISS、P4 は関心の分離です。原則の表と、原則だけを問う方針のレビューの一層目の雛形を足しました。方針のレビューと実装のレビューの結果に、P1 から P4 の指摘が出ます。関心の分離の P4 も含みます。原則の起動は、その原則を問える形があるときだけ走ります。原則を足したので、指摘の数が増えることがあります。条件は [docs/reviews.md](../reviews.md) に書いています。方針のレビューのうち、設計書のレビューは 1 回の起動のままで、原則ごとの起動は PR と範囲のレビューだけです。

### 自分で作った言語のプラグインは、手直しが要りますか

手直しは要りません。言語のプラグインの API に、次のものを足しました。すべて追加で、既存の名前の変更や削除はありません。

- `TypeDecl.abstract` と `MemberDecl.abstract`: 直接インスタンスにできない型と、サブクラスが実装する約束のメソッドを示します。既定は `False` です。
- `StoreFormat.CUSTOM`: 値は「独自の形式」です。文字列を組んで書き、読み戻す保存物の形式です。`StoreFormat` を網羅して場合分けしているプラグインには、新しい値が来ます。
- `ValueSet`、`ComparisonKind`、`StringComparison`、`ValueSetReader`: 値の組と文字列の比較を拾う口です。
- `DefinitionKind`: 値の組の書かれ方が、名前に束ねた定義（`NAMED`）か、名前の無いリテラル（`LITERAL`）かを示します。値の組の読み取りは、これを `ValueSet.kind` に入れて返せます。既定は `UNDETERMINED` で、決めていない言語とプラグインは手直しが要りません。
- `PARAMETER_STORE_MARK`: ファイル名が関数の引数で渡る保存物の名前を「関数名 の引数 引数名」と組むときに、間に挟む文字列です。

`ValueSetReader` を実装しない言語も、そのまま動きます。ただし、その言語のファイルは値の組の表の対象から外れます。

### 方針の資料と判断の地図の見え方は、どう変わりましたか

方針の資料に、次のものが増えました。

- 共変更の表: 履歴から、一緒に変わったファイルの対と強さを示します。
- 値の組の表: 同じ値の組が現れる箇所を示します。組み込みの Python、Java、C#、Swift が対応しています。定義の欄の場所には、名前に束ねた定義なら `パス:行 名前`、名前の無いリテラルなら `パス:行（リテラル）` を出します。読み取り役が決められないときは、場所だけを出します。
- 足した公開の口と呼ぶ側の表: 変更で足した、または引数を足した公開の名前と、変更の後の木の中の呼ぶ側の数を示します。
- 足した型と同じ項目を持つ型の表: 変更で足した、または項目が変わった型と、項目の名前を二つ以上共有する別の型を示します。
- 型の図の注記: 変更で継承か種類が変わった型を示します。

この 2 つの表は Python のファイルだけを読みます。他の言語では、この 2 つの節は出ません。

判断の地図と方針の資料の描き方も、次のように変わりました。

- Python の Protocol を、interface ではなく抽象の class として描きます。
- 型の図に、抽象の印が出ます。言語の宣言から確かに分かる型とメソッドだけに付きます。
- ファイル名が引数で渡る保存物と、独自の形式の保存物は、保存物の表で相手の欄が「（特定できていない）」になります。
- `csv.reader` で読む関数を、CSV を読む側として拾います。
- シーケンス図で、変更に関わる呼び出しだけを残すと矢印が無くなる入口も、直接の呼び出しとともに描きます。リポジトリの中のモジュールを呼んでいて呼び先を解けない呼び出しは、呼び出しの式を名前にした相手への破線の矢印になります。一枚の図に五つまでで、残りは件数で示します。
- シーケンス図の「変更に関わらない呼び出し」の注記に、リポジトリの中の呼び先の名前を五つまで並べます。
- Python のファイルパスの表で、パスを受け取るライブラリの関数（toml、json、yaml、pickle、pandas、numpy の load や dump など）を、そのパスの読み書きとして数えます。
- 技術選定の節で、変更したファイルから消えた技術を他のファイルが使い続けていれば、その場所を添えます。
- 繰り返しの節で、同じ行が見つからなかったときに、照らした行の長さの下限（30 字）を書き、それより短い行は照らしていないと書きます。

### データの置き場の権限は変わりますか

`JIGANE_HOME` のディレクトリ（設定しないときは `~/.local/share/jigane`）を新しく作るときは、所有者だけが読み書きできる権限（0700）で作ります。既にあるディレクトリの権限には触りません。

### エラー文を照合しているスクリプトは、影響を受けますか

受けることがあります。人に見える文面で、次の言葉を言い換えました。副コマンドとオプションの名前は変わりません。変わるのは help とエラー文などの文面です。

| 0.1.3 まで | 0.1.4 から |
| --- | --- |
| 機能レビュー | ファイルのレビュー |
| 差分レビュー式 | 差分のレビュー |
| 外の言語 | 追加の言語 |
| 推し | 候補 |
| プロンプト版（`jigane usage` の表の見出し） | プロンプトの型の版 |

失敗の種類 `language_plugin_unavailable` の見出しは「追加の言語を使えません」になります。種類の名前は変わりません。

文言を照合しているスクリプトは、見直してください。

### Python 以外の言語では、原則を問えますか

図に問える形があれば問います。ただし、足した 2 つの表（足した公開の口と呼ぶ側、足した型と同じ項目を持つ型）は Python のファイルだけを読むので、他の言語では P1 と P2 の起動が見送られやすくなります。他の言語での問える範囲は、後の版で確かめます。

### 方針のレビューの費用の目安は、変わりましたか

PR と範囲のレビューの方針は、起動が 1 本から最大 5 本に増え、全起動の和の目安は 0.5 USD から 0.44 USD になりました。図の起動は常に走り、claude-sonnet-5-5 で上限を 0.36 USD にしました。原則の起動は claude-haiku-5-5 で、1 本の上限を 0.02 USD にしました。原則の起動は、その原則を問える形があるときだけ走り、形が無いものは見送ります。同意の画面と `jigane estimate` の額は、実際に組み立てた起動の上限の和です。すべての原則を問うとき、同意の画面の方針の群の内訳は、`発見役: 図の起動 1 回 × 1 回の目安 0.36 USD + 原則の起動 4 回 × 1 回の目安 0.02 USD = 0.44 USD` と出ます。0.1.3 までは `発見役: 1 回 × 1 回の目安 0.5 USD = 0.5 USD` でした。

この額は起動ごとの上限の積み上げで、実額の予測ではありません。実際の額は、出力の量で変わります。`--model` と `--max-budget-usd-per-call` を渡すと図と原則のすべての起動に効き、`--max-budget-usd-per-call` を渡したときの全体の目安は最大でその 5 倍です。`--model` だけを渡すと上限はそのままなので、原則の起動が上限で見送られることがあります。上限に達する入力の起動は見送られ、残りの結果を保存します。原則の起動が「図から確かめられない」と捨てた候補は、nit にも実装のレビューへの引き継ぎにもしません。起動ごとのモデルは `runs.json` に残り、`jigane usage` は起動のモデルごとに行を分けます。設計書のレビューは 1 回の起動のままで、0.5 USD、claude-sonnet-5-5 です。

入力の大きな差分では原則の起動が見送られ、もっと大きな差分では方針のレビューが走らないことがあります。プロンプトがおよそ 157,000 バイトに達すると原則の起動を、およそ 185,000 バイトに達すると図の起動を見送ります。見送った起動に費用はかかりません。`--max-budget-usd-per-call` で 1 本の上限を上げると走らせられることがあります。Haiku はプロンプトが 100,000 トークンを超えると単価が上がるので、上げる額はその分を見込んでください。

図の形の方針は、起動の前に、プロンプトのバイト数を約 2.25 で割ったトークン数に 1 時間のキャッシュの書き込みの単価を掛け、出力の見込み（図の起動 3,000 トークン、原則の起動 12,000 トークン）を足した額を見積もります。この額が 1 本の上限以上なら、起動せず見送ります。単価は [Anthropic の価格表](https://platform.claude.com/docs/en/about-claude/pricing)（2026-11-04 に確認）に従います。Claude Code 自身のプロンプトの分は数に入らないので、この額は目安で、実額が上限を超えることがあります。既定の上限で見送りが始まる大きさは、原則の起動でプロンプトがおよそ 157,000 バイト、図の起動でおよそ 185,000 バイトです。`jigane estimate` の文と `--json` の `input_cost_usd` は、図の形では出力の見込みを含む額です。単価の表に無いモデルを `--model` で選ぶと最高の単価で見積もります。既定の上限では、原則の起動は出力の見込みだけで上限に達するので、プロンプトの大きさによらず常に見送られます。図の起動は、プロンプトがおよそ 23,600 バイトに達すると見送られます。

### LLM に送るものの文書に、何を書き足しましたか

`docs/data-destinations.md` に、claude が要求に足すものを書きました。ログイン中のアカウントのメールアドレス、環境の節（作業ディレクトリのパス、OS の名前と版）、作業ディレクトリがリポジトリのときのリポジトリの状態の節です。0.1.4 の変更で増えたのではなく、これまでも送られていたものを文書に書いたものです。起動の環境を絞っても入ることを、claude 2.1.308 にログインした環境で確かめました。API キーで認証する場合は確かめていません。
