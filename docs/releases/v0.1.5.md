# jigane 0.1.5 のお知らせ

0.1.5 では、Swift の方針の資料で読める図と表を増やしました。実装とセキュリティの群は、起動を止める大きさの判定を実際の課金に合わせ、差分が大きいときだけシャードを 8 個まで増やすようにしました。あわせて、呼ぶ側の表の数え方、Claude Code へ渡す設定、作業ディレクトリの import の扱い、原則の起動の判断を改めました。保存物の形式は変えていません。文法の取得のやり直しは、通常は要りません。

## 想定される質問

### 更新の後に、必要な操作はありますか

通常はありません。指摘の記録などの保存物の形式は変えていないので、0.1.4 までに作ったレビューの読み替えは起きません。Claude Code の下限も 2.1.308 のままです。

文法の版も変えていないので、`jigane languages fetch` のやり直しは通常は要りません。文法は Python の環境の中に置きます。`uv tool upgrade jigane` では置き場が残り、`uv tool install --force jigane` では置き場が消えることを、uv で確かめました。`pipx upgrade` は確かめていません。環境を作り直したときなど、文法が無いときは、jigane が取得を案内するので、`jigane languages fetch` を走らせてください。

`jigane usage` の表では、原則の起動の行が分かれます。原則の起動のプロンプトの雛形を変えたため、プロンプトの型の版が変わったからです。0.1.4 で始めたレビューを 0.1.5 で続けて実行すると、同じ役の行が、版ごとに分かれて出ます。

### Swift では、何が読めるようになりましたか

Swift の変更で、方針の資料に次の図と表が出るようになりました。

- **判別の流れ図**：`if`、`guard`、`switch`、`return`、`throw` を読みます。`return` の値は `.foo` と `Kind.foo` のようなメンバ参照だけを残します。式としての `if` と `switch` は、`return` の式のときと、本体がその一文だけのときに読みます。変数への代入の右辺に書いた式は読みません。
- **ファイルの名前の組み立て**：`URL`、`FileManager.default`、`Data` と `String` の初期化子、`write(to:)` を読みます。
- **足した型と同じ項目を持つ型**：トップレベルの `struct`、`class`、`actor`、`enum` の、格納プロパティと `case` の名前で照合します。計算プロパティ、`static` と `class` のプロパティ、`extension`、入れ子の型は読みません。
- **足した公開の口と呼ぶ側**：`private` と `fileprivate` が付かない名前を公開の名前として拾います。引数は呼ぶ側が渡すラベルで照合し、外部名が `_` の引数は拾いません。`extension` のメンバは、拡張される型の名前を付けて数えます。同じ名前のオーバーロードは一つの定義に合わせるので、足したオーバーロードは足した引数として出ます。

Swift のレビューの質がどれだけ変わるかは、まだ測っていません。

### Swift で対応していないものは何ですか

副コマンドの引数の表と、保存物の書く側と読む側の表には対応していません。後の版で扱うことを検討していますが、時期と内容は約束しません。言語ごとの対応は、`jigane languages list` で確かめられます。

0.1.4 のお知らせでは、足した 2 つの表が Python だけを読むと書きました。0.1.5 では Swift も読みます。Java と C# は読まないので、方針の資料には対応外の言語として名前が出ます。

### languages list の対応する図が減ったのはなぜですか

0.1.4 までは、読めない図も対応すると示していたからです。足した型と同じ項目を持つ型と、足した公開の口と呼ぶ側は、どの言語でも対応すると出ていました。C# の判別の流れ図も同じです。0.1.5 では、言語のアダプタが読む口を持つかで決めます。

| 言語 | 対応外の図 |
| --- | --- |
| Python | なし |
| Java | 副コマンドの引数、ファイルの名前の組み立て、保存物の書く側と読む側、足した型と同じ項目を持つ型、足した公開の口と呼ぶ側 |
| Swift | 副コマンドの引数、保存物の書く側と読む側 |
| C# | 判別の流れ図、副コマンドの引数、ファイルの名前の組み立て、保存物の書く側と読む側、足した型と同じ項目を持つ型、足した公開の口と呼ぶ側 |

`--json` の出力も同じ内容に変わります。対応の一覧を読むスクリプトがあれば、確かめてください。

### 大きな差分のレビューは、どう変わりますか

実装とセキュリティの群の次の三つが変わります。数字は既定の上限（1 回の起動 0.5 USD）のときの目安です。

**1 本の起動を止める大きさ。** プロンプトがおよそ 230,500 バイトに達すると、その起動を見送ります。0.1.4 では、およそ 375,000 バイトでした。0.1.4 の判定は、課金より少なく入力を見積もっていました。最初の往復の書き込みだけで Claude Code に渡す上限へ届く入力は、費用を使って指摘が 0 件になるので、その手前で止めるようにしました。

**シャードの数。** 通常は最大 4 個のままです。4 個に分けたプロンプトのどれかが止まるときだけ 1 個ずつ増やし、どのプロンプトも止まらない最小の数を選びます。上限は 8 個です。`--max-budget-usd-per-call` で上限を上げると、増えないことがあります。

**断る大きさ。** 4 個に達した差分を 8 個に増やしてもプロンプトが止まるときは、収まるシャードも起動せず、費用を使わずに全体を見送ります。目安はプロンプトの合計で約 1.84 MB（約 230 KB × 8）です。ファイルの大きさに偏りがあれば、もっと小さな差分でも見送ります。そのときは差分を分けて範囲を狭めるか、`--max-budget-usd-per-call` で上限を上げてください。

ファイルが少なく、単位が 4 個に満たない差分は増やせません。この差分は全体を見送らず、収まるシャードだけを走らせ、止まるシャードを記録します。

詳しい判定は [docs/cost.md](../cost.md) に書いています。

### 費用の目安は、どう変わりますか

シャードが増えると、起動の回数が増えるので、同意の画面と `jigane estimate` の額も増えます。8 個なら、発見役だけで 8 回 × 0.5 USD = 4 USD の目安で、これに検証役の分が加わります。同意の画面、`jigane estimate`、実行は、増やした後の同じ数を使います。4 個で収まる差分の起動の回数は変わりません。

Claude Code に渡す上限の額も変わります。0.1.4 までは、上限からプロンプト全体をもう一度入力する額を引いていました。0.1.5 では、最後の一往復の見込み（キャッシュの読み出しと 4,000 トークンの出力）を引きます。引く額が小さくなるので、1 本の起動が打ち切られるまでに使える額は増えます。100,000 バイトのプロンプトなら、渡す上限はおよそ 0.43 USD からおよそ 0.46 USD になります。

`jigane estimate` の文と `--json` の `input_cost_usd` は、実装とセキュリティの群でも出力の見込みを含む額になります。項目の名前は変わりません。

これらの額は目安で、実額の予測でも上限の保証でもありません。Claude Code は上限を往復の合間にしか確かめないので、実額が上限を超えることがあります。

### 呼ぶ側の表の数が増えたのはなぜですか

足したクラス（Swift の型）の呼ぶ側に、これまでの生成と継承に加えて、型注記と式の中で名前を書いた箇所も数えるようにしたからです。データの型のように、生成の外でも名前で使う型が 0 と出ていました。

数え方は、変更の後の木の中で名前を照合するだけで、型は解決しません。同じ名前の別の定義を使う箇所も数えるので、数が増えても、すべてがその型の呼ぶ側とは限りません。省略形の列挙の値（Swift の `.a`）と、文字列で書いた型注記（Python）は数えません。Python の入れ子のクラスは行になりません。そのため、呼ぶ側が 0 でも、数えない形で使っていることがあります。

### LLM に送るものは、どう変わりましたか

Claude Code が要求に足す、リポジトリの状態の節（Git の利用者名、枝、状態、直近のコミットの件名）を切りました。`--settings` に `includeGitInstructions: false` を渡しています。claude 2.1.308 で要求から消えることを確かめました。

環境の節（作業ディレクトリのパス、OS の名前と版）と、ログイン中のアカウントのメールアドレスは、引き続き送られます。`ANTHROPIC_API_KEY` で認証しても入ることを確かめました。切る手段は、確かめた範囲では見つかっていません。送り先と送るものは [docs/data-destinations.md](../data-destinations.md) に書いています。

### PYTHONPATH について、気を付けることはありますか

`PYTHONPATH` に空の項目を入れないでください。先頭や末尾の区切り、続けて書いた区切りは、空の項目になります。

空の項目と `python -m` の先頭の項目は、作業ディレクトリを指します。レビューするリポジトリの根で起動すると、`email.py` のような名前のファイルが、標準のモジュールより先に読まれることがありました。0.1.5 の jigane は、起動の最初に作業ディレクトリを `sys.path` から外します。

ただし、それより前に読まれるものは守れません。`PYTHONPATH` に空の項目があると、そのリポジトリの `jigane/`、`sitecustomize.py`、`functools.py` のようなファイルは、jigane のコードに届く前に実行されます。[SECURITY.md](../../SECURITY.md) にも同じことを書いています。

### 原則の起動の結果は、どう変わりますか

原則の起動（P1 から P4）は、候補を捨てなくなりました。原則に関わる形は、すべて違反か nit かを判断して指摘に入れます。違反とは言い切れない形や迷う形は、nit で出ます。0.1.4 の「図から確かめられない」と捨てる扱いは無くなりました。原則の起動の出力に、捨てた候補はありません。

nit の見え方は変わることがあります。指摘の数や質がどう変わるかは、まだ測っていません。原則の起動の本数と 1 本の上限は変わりません。

### 自分で作った言語のプラグインは、手直しが要りますか

動かすための手直しは要りません。次の口を足しました。

- `DiscriminatorReader`（`discriminator_branches`）: 判別の流れ図に関数の本体の分岐を渡す口です。`SequenceAdapter` の口からこちらへ移しました。
- `TypeFieldReader`（`type_fields`）と `TypeFields`: 足した型と同じ項目を持つ型を読む口です。
- `PublicNameReader`（`added_public_names`）、`PublicName`、`PublicNameKind`: 足した公開の口と呼ぶ側を読む口です。

図の対応は、この口を持つかで決まります。これらを実装しない言語は、3 つの図が対応外になります。`discriminator_branches` を持つプラグインは、判別の流れ図に対応すると数えます。常に `None` を返すだけのメソッドがあれば、消すと対応外として正しく出ます。口は試験的で、jigane の版で変わることがあります。
