# jigane.design

設計書（Markdown）を、見出しの木、Mermaid の図、表に分けます。LLM は呼ばず、Markdown のパーサにも依存しません。

## 主な入口

| 名前 | 役割 |
| --- | --- |
| `parse.parse_design` | 設計書の本文から `DesignDocument`（節の木、図、表）を作ります |
| `mermaid.parse_diagram` | 図の原文から、種類ごとの要素を読み取ります |
| `mentions.extract_mentions` | 設計書が名指した型、修飾名、パス、副コマンド、引数、保存物のファイル名を、節ごとに取り出します |
| `recommend.recommend` | 設計書から名指しを取り出し、いまのコードへ引き当て、突き合わせるファイルを上限つきで推薦し、名指しごとの照合の表を返します |
| `review_documents` | 設計書のレビューの作成と更新（`create_design_doc_review`、`refresh_design_doc`）と、付属の文書の読み込みを持ちます |
| `section_map.build_section_map` | 設計書の節を、`division.SECTION_KINDS` の表に従って判断の地図の箇所と行数にします。LLM は呼びません |
| `division.DIVISION` | 設計書のレビューの受け持ちの表（群の識別子を鍵に、方針の行は観点の集合、実装とセキュリティの行は問う懸念と印を決める見出しの語）です |

設計書の形の観点の文と表、雛形への差し込みの文（`division_text`、`viewpoints_text`）、見出しの語から受け持ちの印を付ける `section_marks` も、この表のモジュールだけが持ちます。観点の識別子の組は範囲外で、`skills.macro.VIEWPOINTS`（M5 を含み、指摘のスキーマの enum に使う）と図だけの雛形にも残ります。図の形が M5 を使うため、`ViewpointId` から導きません。

## 型

| 型 | 持つもの |
| --- | --- |
| `Section` | 階層、題、行の範囲（1 始まり、子を含む）、子の節を持ちます |
| `MermaidBlock` | 図、属する節、柵の行の範囲を持ちます |
| `Table` | 列の名前、行（セルの並び）、属する節、行の範囲を持ちます |
| `ClassDiagram` | 型（名前、ステレオタイプ、項目、メソッド）、関係（両端、種類、記号、ラベル）を持ちます |
| `ErDiagram` | 実体（属性の型、名前、キー、コメント）、関係（両端、多重度、ラベル）を持ちます |
| `SequenceDiagram` | 参加者（名前、別名）、メッセージ（送り手、受け手、文、矢印）を持ちます |
| `FlowchartDiagram` | 節点（id、ラベル）、辺（両端、ラベル、記号）を持ちます |
| `UnsupportedDiagram` | 読めない種類の図です（原文と宣言された種類だけを持ちます） |

## Q&A

### なぜ構造を不変の dataclass で持ち、図の種類を列挙で判別するのですか

構造は不変の dataclass で持ち、図の種類は `DiagramKind` の列挙で判別します。種類ごとの分岐を、型検査の網羅（`match` と `assert_never`）で確かめるためです。不変にするのは、組み立てた後で図の構造が変わらないようにするためです。

### なぜ読めない行を原文のまま残すのですか

読めない行は `Diagram.unreadable` に行番号つきで原文のまま残します。図の原文は `Diagram.source` に残します。読めなかった箇所を黙って落とさず、設計書に書かれていないことを推測しないという方針に沿って、読めない書き方を原文のまま資料に残すためです。

### なぜ Setext の見出しと、引用や入れ子の中の表を対象外にするのですか

Setext の見出しと、引用や入れ子の中の表は対象外です。必要なのは柵、見出し、表の区切り行の判別だけで、Markdown のパーサへの依存を足さずに済むからです。

### なぜ見出しの階層が飛んだ節を、直前のより浅い節の子にするのですか

見出しの階層が飛んだ節は、直前のより浅い節の子にします。最初の見出しより前に置いた構造は節を持ちません（`section` が `None`）。親の無い節を作らず、すべての節を構造の木に載せるためです。`tests/test_design_parse.py` の `test_heading_level_skip_attaches_to_nearest_shallower` が、`#` の次に `####` が来て、その後に `##` が来る設計書で、`####` の節と `##` の節がともに `#` の子になり、`####` の節の階層が 4 のまま残ることを固定しています。

### なぜ flowchart の `subgraph` や `style` などを、読めない行に数えず読み飛ばすのですか

flowchart の `subgraph`、`style` など、節点と辺を宣言しない行は、読めない行に数えず読み飛ばします。予約語の後ろが空白と引数の形のときだけがこれに当たり、`class --> B` のように後ろが辺の記号なら、予約語と同じ名前の節点の辺として読みます。シーケンス図のブロックの開閉と注、クラス図の `direction` も同じです。これらの行は入れ物の囲い、配置、見た目の指定で、節点と辺を宣言しないからです。

### なぜ推薦は LLM を呼ばず、候補をこの順に並べるのですか

推薦は LLM を呼びません。候補は、名指した節の数の多い順に並べ、同数なら直接の引き当てを一段のたどりより上に、さらに同じならパスの辞書順に並べます。試験のファイルは、引き当ての先にもたどりにも入れません。設定の除外と docs の下のソースは、索引と、型、関数、副コマンド、保存物の引き当ての対象から除きます。パスの名指しは、試験を除く全てのファイルを引き当ての先にします。決定的な処理にすると、同じ設計書と同じコードから同じ推しが出るからです。

### なぜ対象のファイルから、隠しディレクトリの下の追跡外のファイルを除くのですか

対象のファイルは、git の下では追跡しているものと、追跡していないが ignore もされていないもの（`git ls-files --others --exclude-standard`）です。追跡外のファイルは、隠しディレクトリ（名前が `.` で始まるディレクトリ）の下を除きます。git の外での扱いと揃えたもので、`.claude/worktrees` のような他の作業の写しを入れないための線です。`.git` を持つ入れ子の作業木は git が一つのディレクトリとして返すので、中のファイルは入りません。追跡外かどうかは、パスを持つ値（`Candidate` と `Location`）が不変の `untracked` として自分で持ち、ファイルを列挙する一か所で決めます。テキストでは「追跡外」、`--json` では `untracked: true` の印が、その値から付きます。

### なぜ地の文の保存物の名前を、定数に持たれているものに限るのですか

地の文（コードスパンの外）の `.json`、`.jsonl`、`.csv`、`.toml` の名前は、作業ディレクトリの Python のソースが定数（`NAME = "x.json"`）として持つ名前に一致するときだけ、保存物の名指しに数えます。定数に無い名前は保存物としては拾わず、実在するファイルの拡張子を持つ名前なら次の項のとおり PATH の候補として扱います。絞りの名前の集合は推薦の側が集めて `extract_mentions` の `stored_names` に渡します。定数に無い `foo.json` まで拾うと雑音が増えるからです。

### なぜ保存物の名指しを、名前を持つ定数の宣言から、その定数を参照する関数のファイルへつなぐのですか

保存物（`review.json` のようなファイル名）の名指しは、名前を文字列の定数（`NAME = "review.json"`）として持つファイルに引き当たります。保存物の名前を持つ全ての行から定数の宣言を探します。さらに一段、その定数を関数の中で参照するファイルを、理由 `reader`（読む側）か `writer`（書く側）で候補に足します。たどりを一段に限るのは、広げると候補がいまのコード全体に近づき、量で押し流す失敗に戻るからです。

### なぜ関数の中の書き込みの呼び出しで、書く側と読む側を分けるのですか

関数の中に書き込みの呼び出し（`write` で始まる名前、`atomic` を含む名前、`dump`（`json.dump`、`yaml.dump`、`pickle.dump`、修飾なしの `dump` を含む）、`rename`、`os.replace`、`shutil.move`、引数一つの `replace`、書き込みの mode（w、a、x、更新の +）の `open`）があれば書く側、無ければ読む側とします。`replace` を引数一つに限るのは、引数が二つの `str.replace(old, new)` と形が同じで、書き込みではないからです。

### なぜ呼び出しの辿りを直接の呼び出しだけに限り、Python だけを対象にするのですか

呼び出しは関数の中の直接の呼び出しだけを見て、別の関数へ渡した先は追いません。参照は、定数を定義したモジュールからの import（`from mod import NAME`）か、モジュール経由の参照（`mod.NAME`）に限り、同じ名前の無関係な識別子は拾いません。この辿りの言語は Python だけで、他の言語の定数は追いません。定義したファイルと、関数の外（import など）だけの参照は足しません。その関数を呼ぶ側のファイルは、もう一段のたどり（理由 `accessor_caller`、候補の種類 `two_step`）として足し、同じ節の数なら直接と一段のたどりより下に並べます。たどりを広げると候補がいまのコード全体に近づき、量で押し流す失敗に戻るからです。

### なぜ地の文と表のセルのパスの形の語を、実在するときだけ名指しに数えるのですか

地の文と表のセルの、パスの形の語（`/` を含む語と、作業ディレクトリに実在するファイルの拡張子を持つファイル名）は、出どころが `PROSE` か `TABLE_CELL` のパスの名指しの候補として返します。推薦の側で、作業ディレクトリに実在するときだけ名指しに数え、実在しない語は照合の表にも出しません。同じ節の同じ名前は、種類が違っても出どころの優先（コードスパン > 図 > 表のセル > 地の文）で一つにまとめ、種類は残したほうのものを採ります。名指しの出どころは `MentionVia` の一つの列挙（`CLASS_DIAGRAM`、`ER_DIAGRAM`、`SEQUENCE_DIAGRAM`、`CODE_SPAN`、`TABLE_CODE_SPAN`、`TABLE_CELL`、`PROSE`）で持ちます。パスの形の語は候補にすぎず、実在の確認が要るからです。

### なぜ小文字だけの語と略語の単独のコードスパンを、名指しに数えないのですか

小文字だけの語（`kind` など）と略語（`JSON` など）の単独のコードスパンは、名指しに数えません。型名か関数名らしい形（大文字始まりで小文字を含む語、下線を含む語、`()` つき）だけを拾います。普通の語と略語まで拾うと、照合の表が荒れるからです。
